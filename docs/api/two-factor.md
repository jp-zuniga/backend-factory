# Two-factor authentication

Time-based one-time codes (TOTP), with recovery codes for when the
authenticator app isn't available. All of the endpoints below except the
login-time challenge (see [Sessions](sessions.md#logging-in)) require an
already-authenticated session.

## Reading status

```http
GET /auth/two-factor/
```

```json title="200 OK"
{
  "confirmed_at": null,
  "enabled": false,
  "pending": false,
  "recovery_codes": 0
}
```

`pending` is true between enrolling and confirming the first code;
`enabled` only flips once confirmation succeeds.

## Enrolling

```http
POST /auth/two-factor-setup/
```

```json title="201 Created"
{
  "secret": "JBSWY3DPEHPK3PXP",
  "uri": "otpauth://totp/api:jdoe?algorithm=SHA1&digits=6&issuer=api&period=30&secret=JBSWY3DPEHPK3PXP"
}
```

Feed the `uri` to an authenticator app (as a QR code or by hand) — it
carries the same secret, issuer and period the API will check codes
against. Enrolling again before confirming just replaces the pending
secret; enrolling on an account that already has a _confirmed_ device
answers `409`.

## Confirming

```http
POST /auth/two-factor-confirm/
Content-Type: application/json

{"code": "123456"}
```

Spends the first code generated by the app to prove enrollment succeeded.
On success, answers `201` with a fresh batch of recovery codes — shown once,
never retrievable again:

```json title="201 Created"
{ "codes": ["ABCD-1234", "EFGH-5678", "..."] }
```

## Recovery codes

Ten single-use codes are issued at confirmation time, and the same call that
confirms enrollment or rotates codes always returns the _entire new batch_ —
old unused codes are invalidated the moment a new batch is issued.

```http
POST /auth/two-factor-recovery/
Content-Type: application/json

{"code": "123456"}
```

Requires spending a currently-valid code (TOTP or an existing recovery code)
to rotate — this replaces the whole set with ten new ones, same response
shape as confirming.

## Logging in with two-factor on

See [Sessions → Logging in](sessions.md#logging-in) for the `202` challenge
response. Redeem it here:

```http
POST /auth/mobile/two-factor/
Content-Type: application/json

{"challenge": "…", "code": "123456"}
```

```json title="200 OK"
{ "access": "…", "refresh": "…", "user": { "...": "..." } }
```

The `code` may be a TOTP code or an unused recovery code — both are accepted
anywhere a second-factor code is asked for. The challenge is single-use: a
second attempt with the same challenge, even with a correct code, is
rejected as `401`. The web variant reads the challenge from its cookie and
returns the tokens the same way login does.

## Lockout

After 5 consecutive failed code attempts (`TOTP_MAX_FAILURES`), the device
locks for 15 minutes (`TOTP_LOCKOUT`) — further attempts answer `429`
regardless of whether the code would otherwise have been correct. A
successful code resets the failure counter.

## Disabling

```http
POST /auth/two-factor-disable/
Content-Type: application/json

{"code": "123456", "password": "hunter2"}
```

Requires both the account's current password _and_ a valid second-factor
code — either alone is not enough to turn protection off. Answers `204` and
removes the device and its recovery codes entirely; re-enabling later starts
enrollment from scratch.
